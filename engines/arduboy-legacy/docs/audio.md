# 1-bit audio for the engine

This is a research and design doc for adding music + sound effects to the
engine. We're targeting **the same 1-bit constraint** as everything else:
a single output pin that can only be **on** or **off**. No DAC, no PWM
hardware mixer — just a speaker pin you flip with software.

The reference for "what's possible with 1 bit" is **Tim Follin** (Agent X,
Solstice, Pictionary, etc) — his music on the ZX Spectrum and NES sounded
impossibly rich for the hardware. The techniques have been studied for
40 years; we're going to implement them ourselves.

## How 1-bit audio actually works

When you flip a pin between high and low at frequency `f`, a speaker
attached to it emits a square wave at `f` Hz. So:

- **Single tone**: drive the pin to alternate at the desired frequency.
  That's a beep.
- **Duty cycle = volume**: the *width* of the high portion vs low controls
  perceived volume. Pure 50/50 = loudest; 1/99 = barely audible click.
- **Multiple voices on one pin**: you can't actually mix two square waves
  in the speaker — there's only one output. So we get "mixing" by
  *time-multiplexing*: the CPU very rapidly alternates between voices in
  an interrupt service routine. The speaker hears the combined click
  pattern as a chord.

Three families of technique do this:

### 1. Pulse Frequency Modulation (PFM) / "pin pulse"

Each voice owns a counter. Every audio-ISR firing, decrement counters; when
one underflows, emit a short click and reload the counter with a value
derived from the note's frequency. Adding more voices is cheap (8+ feasible)
but bass is thin because the duty cycle is tiny — the click is brief.

Used by: Octode, Qchan, Huby, Special FX engines.

### 2. Pulse Interleaving / XOR

The audio ISR maintains 2-3 software square-wave generators and **XORs**
their current high/low states to produce the pin output. This produces real
audible voices with body, including bass — but you're typically capped at
2-3 channels because the math gets expensive.

Used by: Tritone, Savage, Wham!, **Phaser1**.

### 3. PWM "level-faking" (the Follin trick)

Run a *very fast* ISR (much faster than the audio frequency) that emits a
pulse whose **width** encodes a synthesized sample value. Five software
counters added together → a 5-voice "additive" mix. The CPU is doing a
crude DAC in software.

What made Follin's music sound so much better than other PWM engines:
- **Composed around the engine's non-linearities** — Follin retuned every
  note when the chord harmonic content shifted, because the engine's
  apparent pitch drifted with chord density
- **Heavy arpeggios** to fake chords without paying for more voices
- **Envelope/portamento/phasing baked into the pattern data** — expression
  was tracked, not generated by an envelope module

Used by: **Agent X engine**, Phaser1.

## What we're going to build

A 4-phase plan, each phase produces something audible:

### Phase 1 — Hardware setup + single tone (~30 bytes flash)

- Use Timer3 (Timer1 is the frame clock). The Arduboy speaker is on PC6
  which maps to OC3A — we can use **CTC mode with toggle-on-compare-match**
  so the pin flips automatically every time the timer hits the compare
  value. Zero CPU between toggles.
- API: `audio::play_tone(hz, duration_ms)`
- Result: every game can beep on demand.

### Phase 2 — sfxr-style SFX synthesis (~200 bytes flash, ~30 bytes RAM)

A single SFX = ~12 bytes of synthesis params (start freq, freq slope,
duration, vibrato, sweep, square/noise type). The audio ISR holds an
"active SFX" struct and modulates the timer compare value frame-by-frame
according to those params. No baked PCM samples — everything synthesized
on the fly.

Six game sounds to start:
- `SFX_SHOOT` — short upward chirp
- `SFX_HIT_ENEMY` — quick downward zap
- `SFX_KILL_ENEMY` — descending triangle thunk
- `SFX_PLAYER_HIT` — harsh noise burst
- `SFX_DEATH` — long descending wail
- `SFX_MENU_SELECT` — clean two-tone

Each one is ~12 bytes of params we tune by ear. Total flash cost for the
SFX library: under 100 bytes of data + ~150 bytes of synth code.

Reference: [sfxr](https://www.drpetter.se/project_sfxr.html) and
[bfxr](https://www.bfxr.net/v1/) are existing tools that do exactly this
on PC. We're porting the *concept*, not the code.

### Phase 3 — Single-channel music (~300 bytes flash for the engine)

A "song" is a PROGMEM array of `(note_index, duration_ticks)` pairs, plus
a pattern + order layout for repetition. The engine steps through them,
loading each note's frequency into the timer compare value. **Monophonic**
but immediately produces real melodies — perfect for testing the file
format, the playback timing, and the workflow without the complexity of
multiple voices.

Songs cost ~2 bytes per note. A 60-second melody at 4 notes/second is
~480 bytes flash.

### Phase 4 — Multi-channel pulse-interleaved music (~600 bytes flash)

The Follin step. Implement **pulse interleaving / XOR** for 2-3 channels.
Each channel maintains its own square-wave phase counter; the audio ISR
ticks all of them and XORs their states to the speaker pin. Bass in one
channel, melody in another, optional drum in a third.

We'll write the engine ourselves but informed by reading these references
(don't port the code — read the algorithm and rewrite for AVR/C++):

- [utz82 / ZX-Spectrum-1-Bit-Routines](https://github.com/utz82/ZX-Spectrum-1-Bit-Routines) — canonical Z80 source for ~30 different engines. The Phaser1 source is a good study target.
- [The Sound of 1-bit (Game Journal)](https://www.gamejournal.it/the-sound-of-1-bit-technical-constraint-as-a-driver-for-musical-creativity-on-the-48k-sinclair-zx-spectrum/) — academic survey of every major beeper engine
- [The 1-bit forum tutorial](http://randomflux.info/1bit/viewtopic.php?id=21) — practical comparison of the engine families
- [Tim Follin / Agent X engine technical notes](http://www.ntmusic.org.uk/?p=505)

### Phase 5 — Composition tool (later, optional)

Once we have an engine that plays a song, we need to write songs without
hand-editing byte arrays. Two organic options:

**Option A: text DSL**
A `.song` text file like:
```
@instrument lead square attack=1 decay=10
@instrument bass square attack=0 decay=20

@pattern intro
  ch1: C4q E4q G4q E4q
  ch2: C2h    G2h
@order intro intro
```
A small Python script parses it into the engine's bytecode. You compose
in any text editor; preview by flashing.

**Option B: tiny web tracker**
A piano-roll-style web UI in HTML/JS. Plays back via WebAudio using the
*same synthesis algorithm* we run on-device, so what you hear in the
browser matches what you'll hear from the speaker. Exports the same
bytecode.

I'd start with the text DSL — faster to build, easier to version-control,
and once we know what the data shape needs to be we can wrap a UI around
it later.

**Existing references for the tool side:**
- [Shiru's 1tracker](https://shiru.untergrund.net/1bit/) — desktop tracker
  supporting 50+ beeper engines. Open source. Worth reading the source for
  song-format ideas even though we won't use it directly.
- [Beepola](http://shiru.untergrund.net/1bit/pivot/entry.php?id=40) —
  Windows tracker, simpler UI. Good for hearing what the engines sound
  like before we build our own.
- [ATMlib](https://github.com/harbaum/ATMlib) and
  [ATMlib2](https://github.com/moduscreate/ATMlib2) — Arduboy-specific
  tracker library. Worth reading the song-format header to see how others
  packed pattern/order/instrument data into AVR-friendly bytes. We won't
  link against it (the project rule is no third-party libraries) but the
  data shape is informative.

## SFX vs music: how they coexist

Standard chiptune trick: when an SFX fires, **temporarily replace one
music channel** with the SFX synth. The music keeps playing on the other
channels; the SFX rides on the channel its priority bumped. When the SFX
ends, the music channel resumes from where it would be. This gives you
audible feedback without ducking the entire soundtrack.

For now (with no music), the SFX engine just owns the pin entirely
during effect playback.

## Engine architecture

```
engine/
  audio.h           — public API: tone, sfx, music, mute
  audio.cpp         — engine-side: SFX synthesis, music stepper

platform/arduboy/
  audio_arduboy.cpp — Timer3 setup, ISR, OC3A pin handling
```

The platform layer owns the timer + ISR + pin. The engine owns:
- The SFX parameter struct + synth math
- The music stepper that walks pattern data from PROGMEM
- A small mixer that decides "which voice goes to the pin this tick"

The platform's ISR calls a single `engine::audio::tick()` function each
firing — the engine does all the synthesis decisions, the platform just
moves the pin.

## Footprint forecast

| Component           | Flash  | RAM   |
|---------------------|--------|-------|
| Timer3 + tone       | ~30 B  | 4 B   |
| SFX engine          | ~200 B | 12 B  |
| 6 baked SFX defs    | ~80 B  | 0 B   |
| Mono music engine   | ~300 B | 16 B  |
| Multi-channel music | ~600 B | 32 B  |
| First song (~30s)   | ~250 B | 0 B   |
| **Total budget**    | ~1.5KB | ~70 B |

We're at ~33% flash and ~75% RAM today. Audio adds ~5% flash and ~3% RAM.
Comfortable.

## Why we're not using any libraries

ATMlib, ArduboyTones, ArduboyPlaytune — all exist, all work. We're not
using them because the project rule from day one was **no third-party
HAL or audio code**. Building this from raw `avr-gcc` is the entire
point. The references above are for **reading**, not depending on.
